# SM_instruction: контекст для разработки

Этот файл — короткая карта проекта для следующих сессий. Перед изменениями сверяйся также с
[`README.md`](README.md) и подробной моделью в [`docs/PLAN.md`](docs/PLAN.md).

## Назначение и текущий этап

Веб-приложение университетского мероприятия «СМ. Инструкция по выживанию». Команды выбирают
персонажа, записываются на точки по временным слотам, получают баллы и прокачивают характеристики.
Есть роли администратора, старосты, студента и организатора точки.

Текущий функциональный каркас готов. Реальные тексты, организации, изображения, расписание и
правила прокачки пока частично заменены заглушками. Для партнёрских баннеров уже есть два
mobile-first формата-заглушки; реальные изображения, тексты и ссылки ещё не получены.

## Стек и запуск

- Rust 2021, axum 0.8, tokio, SQLx 0.8.
- SQLite в режиме WAL: пул чтения до 8 соединений и отдельный пул записи из 1 соединения.
- Vanilla HTML/CSS/ES modules, без npm и сборщика; бэкенд раздаёт каталог `static/`.
- Bearer-сессии хранятся в SQLite, пароль хешируется Argon2.

Локальный запуск:

```powershell
Copy-Item .env.example .env
cargo run
```

Перед сдачей изменений:

```powershell
cargo fmt --all -- --check
cargo clippy --all-targets --all-features -- -D warnings
cargo test --all-targets
$files = rg --files static -g '*.js'
foreach ($file in $files) { node --check $file }
```

Для smoke-тестов не использовать рабочий `data.db`: задавать временный `DATABASE_PATH` и отдельный
`BIND_ADDR`. Локальные БД, `.env`, `target/` и настройки инструментов игнорируются Git.

## Карта кода

- `src/main.rs` — конфигурация, HTTP-маршруты, middleware и раздача статики.
- `src/db.rs` + `src/schema.sql` — подключение, совместимые миграции и стартовые данные.
- `src/auth.rs` — регистрация, вход, сессии и extractor текущего пользователя.
- `src/models.rs` — DTO, доменные константы типов точек и прокачки.
- `src/handlers/booking.rs` — правила бронирования и отмены.
- `src/handlers/organizer.rs` — список визитов и начисление баллов организатором.
- `src/handlers/public.rs` — каталоги, слоты, рейтинг, команда, персонаж.
- `src/handlers/admin.rs` — административные CRUD-операции.
- `static/app.js` — точка входа и hash-router.
- `static/js/` — экраны и общие фронтенд-модули; `cabinet.js` содержит кабинет и админку.
- `static/content.js` — редактируемые тексты, карточки организаций и пути к изображениям.
- `static/style.css` — mobile-first стили, разбитые комментариями на секции.

## Инварианты домена

- Только староста бронирует обычную точку для своей группы.
- Бронирование открывается за 15 минут до начала и закрывается в конце слота.
- У команды не больше одной активной обычной брони; обязательные назначения идут параллельно.
- Одну точку нельзя повторно пройти, пока бронь активна или завершена.
- `noc` получает оценки `test` и `task`, `activity` — только `task`, `mandatory` — без баллов.
- Все записи сериализованы через `db_w`; проверки вместимости и баланса должны оставаться в той же
  транзакции, что и изменение.
- Подтверждения на фронтенде делаются через `ask`/`askText`, а не `confirm`/`prompt`.
- Данные из API перед вставкой через `innerHTML` экранируются функцией `esc`; не добавлять inline
  handlers, использовать `data-act` и делегирование событий.

## Контент и партнёрские баннеры

Организации хранятся в `points` с типом `noc`: карточка, расписание и бронирование связаны стабильным
`points.id`. Логотип и галерея задаются полями `logo_url` и `image_urls`; локальные ассеты хранить в
`static/img/`, загруженные админом файлы попадают в игнорируемый `static/uploads/`. Баннеры на витрине и в радиальном меню настраиваются через `AD_BANNERS` в
`static/content.js`; пустой `href` оставляет заглушку некликабельной.

## Известный технический долг

- Интеграционных тестов HTTP/API пока нет; есть только точечные unit-тесты и ручной smoke-test.
- Нет rate limit для входа и регистрации.
- Значения `admin/admin` и `change-me` нельзя использовать в окружении; перед деплоем нужен сильный
  `ADMIN_PASSWORD` и отдельная проверка конфигурации при старте.
- Сессионные токены лежат в БД в исходном виде, просроченные сессии автоматически не очищаются.
- Деплой, TLS, резервное копирование SQLite и нагрузочный прогон ещё не оформлены.
- Реальные данные заказчика и правила стоимости прокачки не получены.

## Синхронизация с демо-сервером

- Перед синхронизацией и очередным обновлением по умолчанию считать базу данных на демо-сервере
  источником актуальных пользовательских данных: сначала забирать её с сервера, если пользователь
  явно не указал обратное и это не создаёт прямого архитектурного конфликта (например, при
  несовместимой миграции схемы). После этого накатывать локальные изменения и возвращать базу на
  демо-сервер без потери данных.
- Демо развёрнуто на `https://miandic-demo.ru` (`77.110.127.218`): приложение находится в
  `/opt/sm-instruction`, работает как `sm-instruction.service` на `127.0.0.1:18080`, nginx-конфиг —
  `/etc/nginx/sites-available/miandic-demo.ru`. HTTPS проходит через существующий Xray Reality на
  nginx `127.0.0.1:8444`; домен добавлен в `serverNames` X-UI.
- На этом демо по явному требованию владельца сохранять учётную запись `admin/admin`, если он не
  попросил изменить её отдельно.
