# Боевой сервер

Домен: https://smsurvival.bmstu.ru, SSH: `root@195.19.34.20:22`.
Среда: Ubuntu 24.04, LXC, 4 ГБ RAM, диск 10 ГБ. Порт SSH, парольный вход и правила
файервола при настройке не изменялись. Создан отдельный ключ, root-пароль заменён.

## Доступ и секреты

Локальные реквизиты находятся в `private-deploy/credentials.json`, приватный ключ —
`private-deploy/id_ed25519`, зафиксированный ключ сервера — `private-deploy/known_hosts`.
Вся папка исключена из Git; доступ Windows ограничен текущим пользователем и SYSTEM.
Сохраните её резервную копию в менеджере паролей: клонирование репозитория секреты не восстановит.

Из корня проекта в PowerShell:

```powershell
ssh -i ./private-deploy/id_ed25519 -o UserKnownHostsFile=./private-deploy/known_hosts root@195.19.34.20
```

Пароль админа сайта также находится в `credentials.json`.
На сервере конфигурация — `/etc/sm-instruction/app.env`, доступна только root.
Изменение `ADMIN_PASSWORD` в env не меняет пароль уже существующей учётной записи в БД.
По явному запросу владельца от 03.09.2026 на боевом сервере установлен вход `admin/admin`.
В env задано `ALLOW_ADMIN_ADMIN=1`: исключение разрешает только эту конкретную пару;
остальные проверки конфигурации остаются включены. Коды регистрации выдаются
админом только организаторам точек.

## Схема

nginx принимает HTTP/HTTPS, перенаправляет HTTP на HTTPS и проксирует приложение на
`127.0.0.1:18080`. Certbot обслуживает сертификат и его продление. Приложение работает
как `sm-instruction.service` от пользователя `sm-instruction`, сборка — от `sm-build`.

| Путь | Назначение |
| --- | --- |
| `/opt/sm-instruction/releases/<id>` | Код, бинарник и статика конкретного выпуска; владелец root |
| `/opt/sm-instruction/current` | Символическая ссылка на активный выпуск |
| `/var/lib/sm-instruction/data.db` | Рабочая SQLite, WAL/SHM рядом |
| `/var/lib/sm-instruction/uploads` | Загруженные изображения; ссылка из `current/static/uploads` |
| `/var/backups/sm-instruction` | 14 последних архивов: БД, загрузки, env и идентификатор выпуска |
| `/opt/sm-instruction/build` | Исходники и кэш сборки, не рабочие данные |

systemd ограничивает запись приложения каталогом данных, запрещает повышение привилегий,
задаёт лимит памяти 768 МБ и перезапуск при сбое. SIGTERM завершает активные запросы;
после 30 секунд systemd принудительно остановит зависший процесс. Перед запуском проверяются
сильный пароль и пути конфигурации. nginx ограничивает вход/регистрацию до 10 запросов
в минуту с burst 20 на IP. Для общей университетской NAT-сети лимит может потребовать настройки.

## Первичные данные

При запуске 03.09.2026 демо `77.110.127.218` было недоступно по SSH с двух маршрутов.
Первый боевой запуск был выполнен с новой базой и стартовыми заглушками приложения.
Затем 03.09.2026 по явному запросу владельца прод синхронизирован с локальным `data.db`
и каталогом `static/`: 6 организаций, 2 активности, 3 обязательные точки, 13 групп,
4 персонажа, 3 пользователя, 27 слотов, 10 броней. Пароль админа на проде установлен в `admin`.
Локальные сессии не переносились; потребуется заново войти. Исходная локальная база не изменена.
Перенос с демо не выполнялся.

По умолчанию боевая БД остаётся источником для следующих боевых обновлений.
Замена локальным состоянием допускается только по явному указанию владельца, как при этой синхронизации.
Миграцию с демо согласовывайте отдельно: остановка записей на обоих экземплярах,
SQLite backup API, перенос uploads, проверка схемы, смена демо-пароля админа и отзыв
демо-сессий в переносимой копии. Никогда не копируйте только `.db` работающей WAL-базы.

## Обновление

1. Проверить проект локально. Каждую команду выполнять только после успешной предыдущей:

   ```powershell
   cargo fmt --all -- --check
   cargo clippy --all-targets --all-features -- -D warnings
   cargo test --all-targets
   $files = rg --files static -g '*.js'
   foreach ($file in $files) { node --check $file; if ($LASTEXITCODE -ne 0) { throw $file } }
   ```

2. Создать архив из явного списка исходников. Базы, `.env`, ключи и uploads в него не входят:

   ```powershell
   $release = Get-Date -Format 'yyyyMMdd-HHmmss'
   tar --exclude=static/uploads --exclude=__pycache__ -czf "private-deploy/source-$release.tar.gz" Cargo.toml Cargo.lock src static deploy
   scp -i ./private-deploy/id_ed25519 -o UserKnownHostsFile=./private-deploy/known_hosts "private-deploy/source-$release.tar.gz" "root@195.19.34.20:/opt/sm-instruction/build/source-$release.tar.gz"
   ssh -i ./private-deploy/id_ed25519 -o UserKnownHostsFile=./private-deploy/known_hosts root@195.19.34.20 "bash /opt/sm-instruction/current/deploy/build-release.sh /opt/sm-instruction/build/source-$release.tar.gz $release"
   ```

   Сборка использует Rust 1.94.0, `Cargo.lock`, `--release --locked -j 2`. Приложение
   продолжает работать. Новый выпуск содержит `SHA256SUMS`.

3. Проверить миграции: прогнать новый бинарник на SQLite-копии из свежего backup с отдельным
   `DATABASE_PATH` и `BIND_ADDR=127.0.0.1:18081`. Не использовать для smoke рабочую базу.
   Скрипт активации не заменяет БД, но миграции приложения выполняются при старте.

4. Активировать:

   ```powershell
   ssh -i ./private-deploy/id_ed25519 -o UserKnownHostsFile=./private-deploy/known_hosts root@195.19.34.20 "bash /opt/sm-instruction/current/deploy/activate-release.sh /opt/sm-instruction/releases/$release"
   curl.exe --fail https://smsurvival.bmstu.ru/api/health
   ```

   Скрипт делает backup, переключает ссылку, перезапускает сервис и проверяет health.
   При провале возвращает предыдущую ссылку. **Обратную миграцию БД он не выполняет.**
   Для несовместимых миграций нужен отдельный план восстановления. Изменения systemd/nginx
   при обычном обновлении кода автоматически не устанавливаются: проверяйте их отдельно.
   `deploy/nginx.conf` — исходный HTTP-шаблон; не затирайте им работающий TLS-конфиг.

## Автоматическое обновление из GitHub

Подготовлена служба `sm-instruction-github-sync.service` и таймер
`sm-instruction-github-sync.timer`: проверка `Miandic/SM_instruction`, ветка `main`,
через две минуты после завершения предыдущей проверки. Работает без GitHub-токена
для публичного репозитория. Локальные незакоммиченные изменения не отправляются.

Скрипт `deploy/github-sync.py` устанавливается отдельно в
`/usr/local/lib/sm-instruction/`; автоматически себя не обновляет. Получение кода,
Rustfmt, Clippy, тесты, release-сборка и проверка синтаксиса JS выполняются от
`sm-build`. Пробный запуск использует SQLite backup рабочей БД и отдельный порт
18081. Затем штатная активация создаёт резервную копию, переключает выпуск,
перезапускает приложение и проверяет health; при отказе возвращает предыдущий код.
Рабочая БД, uploads и env остаются на сервере.

Изменения `src/db.rs` или `src/schema.sql` блокируются сравнением с
`/var/lib/sm-instruction-deploy/approved-migrations`. Для их выпуска сначала
проверить миграции вручную, выполнить штатный деплой и обновить одобренный SHA-256
конкатенации этих двух файлов. Автоматического восстановления старой БД нет.
Старые выпуски сохраняются; следите за свободным местом.

Установка требует Git, Node.js, Rust 1.94.0 с компонентами rustfmt и clippy.
Скопировать три файла `github-sync.py`, `sm-instruction-github-sync.service`,
`sm-instruction-github-sync.timer` в `/tmp`, затем выполнить
`deploy/install-github-sync.sh` от root. Установщик запускает первый деплой,
но не включает таймер. Начальный отпечаток миграций берётся из исходников
первого боевого выпуска `/opt/sm-instruction/build/source`.

После успешного первого деплоя:

```bash
systemctl enable --now sm-instruction-github-sync.timer
systemctl list-timers sm-instruction-github-sync.timer
journalctl -u sm-instruction-github-sync.service -n 80 --no-pager
cat /var/lib/sm-instruction-deploy/deployed
```

Ручная проверка/обновление: `systemctl start sm-instruction-github-sync.service`.
Остановка будущих проверок: `systemctl disable --now sm-instruction-github-sync.timer`.
Уже выполняющийся деплой этой командой не останавливается.

## Проверки и журналы сервера

На сервере:

```bash
systemctl status sm-instruction nginx --no-pager
journalctl -u sm-instruction -n 100 --no-pager
tail -n 100 /var/log/nginx/sm-instruction.error.log
curl --fail http://127.0.0.1:18080/api/health
nginx -t
systemctl list-timers sm-instruction-backup.timer certbot.timer
df -h /
```

Журналы приложения — journald (до 150 МБ), nginx — штатный logrotate.
Обновления безопасности автоматические, автоматическая перезагрузка запрещена.
Ядро LXC обслуживает владелец гипервизора. Внешний мониторинг и оповещения пока не подключены.

## Резервное копирование и восстановление

Ежедневно в 03:15 UTC с задержкой до 10 минут выполняется согласованный SQLite backup,
`integrity_check`, архивирование загрузок и env. Сохраняются 14 последних архивов,
включая ручные и преддеплойные. Архивы содержат секреты и доступны только root.

```bash
systemctl start sm-instruction-backup.service
journalctl -u sm-instruction-backup.service -n 20 --no-pager
ls -lt /var/backups/sm-instruction
certbot renew --dry-run
```

Скачайте выбранный архив в `private-deploy/` через `scp` с теми же SSH-параметрами.
Первый проверенный архив сохранён локально. Регулярной внешней копии пока нет:
архивы на том же диске не защищают от потери контейнера.

Для восстановления сначала проверить архив в отдельном каталоге (`tar -tzf`, распаковка,
`sqlite3 data.db 'PRAGMA integrity_check; PRAGMA foreign_key_check;'`). Затем остановить
приложение, сохранить текущие `data.db`, `data.db-wal`, `data.db-shm` и uploads в отдельную
резервную папку, восстановить БД и uploads из **одного** архива, выставить владельца
`sm-instruction:sm-instruction`, выбрать совместимый выпуск из `release.txt`, запустить
сервис и проверить health, вход и карточки. Не оставлять старые WAL/SHM рядом с восстановленной БД.
Не откатывать env без проверки актуальности паролей. Восстановление старой БД теряет
записи после момента архива; это отдельное осознанное действие.

## Границы готовности

Инфраструктурное развёртывание не означает готовность контента к мероприятию.
Остаются реальные тексты, изображения, расписание, правила прокачки, нагрузочный прогон,
внешние оповещения и регулярный внешний backup. Токены сессий приложения пока хранятся
в БД открытым текстом; существующий долг описан в `AGENTS.md`.
